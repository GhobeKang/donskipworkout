# DON'T SKIP 방장·챌린지 시스템 기획서

- 작성일: 2026-09-30
- 문서 상태: 구현을 위한 제안 기준안 v1.1. 아래 정책·수치는 제품 결정안이며 이미 구현된 기능이 아니다.
- 범위: 방 개설, 초대, 룰북 합의·게시 알림, 개시, 운동 소요 시간 측정, 인증·기록 누적, 평가, 결과 확정, 다음 회차, 방장 알림, 운영 예외.
- v1.1 변경: 운동 타이머·공개·집계 기준 추가, 룰북 게시 완료 시 로컬 알림과 원격 푸시의 가능 범위 확정.
- 제외: 과금·결제·구독·상금·예치금·환전·현금 정산. 이 문서는 어떤 금전 기능도 전제하지 않는다.

## 1. 제품 목표와 핵심 결정

친구들이 정해진 기간에 운동 약속을 함께 지키고, 방장은 누가 얼마나 참여했는지 확인하고 필요한 시점에 독려한다. 참가자는 기존 개인 운동 기록을 그대로 사용한다.

방장이 관리하는 것은 모집, 합의, 진행 확인, 독려, 다음 회차다. 인증의 집계와 성적 판정은 서버가 고정된 룰북에 따라 수행한다. 방장도 자신의 결과를 수정할 수 없다.

| 항목 | v1 결정 |
| --- | --- |
| 방과 회차 | 방은 구성원·초대·과거 결과가 남는 공간, 회차는 별도 룰북·기간·참가자·결과를 가진 도전 |
| 인원 | 회차당 2~10명, 방장은 참가자에 포함 |
| 기간 | 7일·14일·28일 중 선택 |
| 주간 기준 | 시작일부터 연속된 7일을 한 평가 구간으로 사용. 월~일 고정 아님 |
| 목표 | 모든 참가자에게 동일한 구간당 운동일 수 1~7일. 기본 3일 |
| 시작 | 전원 동의 후 방장이 개시 예약. 가장 빠른 시작은 다음 날 00:00 |
| 시간대 | v1은 Asia/Seoul 고정. 기기·여행지 시간대로 바뀌지 않음 |
| 인증 | 사진 필수 / 사진 또는 수동 중 하나를 회차 시작 전에 선택 |
| 운동 소요 시간 | 별도 운동 타이머로 측정. 명시적 일시정지는 제외하고 세트 사이 휴식은 포함 |
| 시간의 평가 용도 | 참고 기록이며 v1 출석 자격·달성 점수에 넣지 않음. 미측정은 0분과 구분 |
| 룰북 게시 알림 | 공식 게시 성공 시 서버 알림함·원격 푸시 요청. 로컬 알림만으로 앱 종료 상태의 새 게시를 전달할 수 없음 |
| 인정 횟수 | 한 평가일에 최대 1일. 하루 여러 운동·중복 업로드는 추가 점수 없음 |
| 최종 성공 | 모든 7일 구간의 목표를 각각 달성. 다른 구간의 초과 출석으로 보충 불가 |
| 결과 | 순위 없이 개인 달성·미달·중도 종료를 표시. 전원 달성 시 공동 성공 |
| 기간 연장 | 기존 회차 마감을 바꾸지 않고 같은 방에 다음 회차를 생성 |
| 재촉 | 방장이 요청하고 서버가 권한·진행·빈도와 방해 금지 시간을 확인해 발송 |
| 공개 | 출석 요약은 참여 조건. 사진과 세트 상세는 별도 선택 동의 |

성공 지표는 방 개수 자체보다 초대 후 실제 참여, 인증 지속, 다음 회차 재참여다. 사진 제출은 운동 수행·강도·헬스장 방문을 완전히 입증하지 못하므로 화면에도 “제출 기준 충족”으로 설명한다.

| `server/app/photo_routes.py` | 당일 사진 제출, 사용자별 동일 이미지 해시 중복 검사, `submission_id` 재요청 처리 존재 |

| 세트 기록 | 과거 날짜를 수정할 수 있음. 세트만 입력한 기록은 출석 완료와 다름 |
| `started_at`, `completed_at` | 각각 출발 버튼·출석 인증과 연결돼 있음. 차이를 운동 소요 시간으로 재사용하지 않고 별도 타이머 데이터 추가 |
| `server/app/sharing.py`, `personal_report.py` | 개인 목표 이력·월~일 주간 분석에 연결됨. 회차별 시작일과 고정 룰북을 쓰는 새 평가기 필요 |

| `app/_lib/notifications.js` | 기기 로컬 예약 알림만 존재. 사용자 간 원격 푸시·서버 알림함은 새로 필요 |
| 로그인 | 자체 HttpOnly 세션, 인증 요청마다 갱신하며 유휴 만료 기본 400일. 만료된 경우 알림 클릭·초대 링크의 목적지를 재로그인 뒤 복원해야 함 |
| 앱 연결 | 초대 코드·초대 웹페이지·검증된 앱 링크·가입 후 목적지 복원은 새로 필요 |

기존 개인 목표 설정을 변경해도 진행 중인 회차 목표는 변하지 않는다. 개인 리포트의 과거 수정 가능성과 회차 결과의 확정성을 분리한다.

## 4. 상태와 전환

### 4.1 방과 회차 상태

방 상태는 `open`, `archived`다. `open` 방은 과거 회차를 보존하고 다음 회차를 만들 수 있다. 초안·동의·예약·진행·정산·검토 중 회차가 하나도 없는 경우에만 보관 처리한다. 보관은 결과 삭제가 아니며 참여했던 회차의 허용된 결과는 계속 열람할 수 있다.

| 회차 상태 | 의미 | 허용되는 다음 상태 |
| --- | --- | --- |
| `draft` | 모집·룰북 초안 작성 중 | `awaiting_consent`, `cancelled` |
| `awaiting_consent` | 게시된 룰북에 참여 동의를 받는 중 | 수정 시 동의 초기화, `scheduled`, `cancelled` |
| `scheduled` | 명단·룰북 고정, 개시 시각 대기 | `active`, `awaiting_consent`, `cancelled` |
| `active` | 인증·기록 누적 중 | `settling`, 운영 사유의 `voided` |
| `settling` | 종료 후 24시간 검산·이의 접수 | `finalized`, `review_required`, `voided` |
| `review_required` | 기술 오류를 확인할 때까지 확정 보류 | `finalized`, `voided` |
| `finalized` | 결과 버전 확정 | 기존 버전은 유지, 정정 시 새 버전 발행 |
| `cancelled` | 개시 전 취소 | 종료 상태, 성적 없음 |
| `voided` | 서버 장애·중대한 오류 등으로 평가 무효 | 종료 상태, 달성·미달 성적 없음 |

한 방에는 기간이 겹치는 회차를 둘 수 없다. 단, 현재 회차가 진행·정산 중이어도 후속 회차 1개를 초안·동의·예약 상태로 준비할 수 있다. 현재 회차의 정산과 다음 회차의 인증 기간은 겹쳐도 된다.

### 4.2 참가 상태

- 개시 전: `invited` → `joined_pending` → `consented`. 초대 전달은 계정 가입이나 참여 완료를 의미하지 않는다.
- 개시 이후: `active` → `completed`, `withdrawn`, `removed` 중 하나. `completed`는 기간을 끝까지 마쳤다는 뜻이고 목표 달성 여부는 결과 필드로 구분한다.
- 방 구성원이어도 해당 회차에 동의·등록되지 않으면 그 회차 참가자가 아니다.
- `invited`는 연락처를 수집한 초대 명단이 아니라 수신자가 다음 회차 제안을 받은 상태에도 사용한다. 공개 초대 링크만 발급한 경우 참가자 행을 미리 만들지 않는다.

## 5. 방 개설 → 초대 → 룰북 작성

### 5.1 방 개설

방장은 이름(2~30자), 설명(최대 300자), 정원(2~10명)을 입력한다. 초안 회차와 대기실을 함께 만든다. 방장 자신은 첫 참가 후보가 된다.

이때 목표·기간을 임시로 적을 수 있지만 확정된 약속으로 표시하지 않는다. 대기실에는 “룰북 작성 중 · 아직 시작하지 않았습니다”를 명시한다.

### 5.2 초대 링크와 코드

- 같은 초대에 HTTPS 링크와 입력용 코드(예: `AB7K-9Q2M`)를 함께 제공한다.
- 링크는 해당 회차 대기실을 가리킨다. 이전 회차 링크가 새 회차에 자동 가입시키지 않는다.
- 앱 설치 시 앱의 참여 화면을 열고, 미설치 시 웹 초대장과 설치 버튼·코드를 제공한다.
- v1은 앱에서 로그인·룰북 동의·참여를 완료한다. 웹은 초대 미리보기만 제공한다.
- 설치 후에는 원래 링크를 다시 누르거나 코드를 입력한다. 설치 전 링크의 자동 복원은 v1 보장 사항이 아니다.
- 재로그인 동안 초대 목적지를 유지하되, 로그인 성공 후 서버에서 초대 상태를 다시 확인한다.
- 링크·코드 입력만으로 참여 확정하지 않는다. 먼저 대기실에 참여하고 최종 룰북에 동의해야 한다.

초대 유효기간은 발급 후 7일이며, 개시 예약·회차 취소·방장 폐기 중 먼저 발생한 시점에 닫힌다. 재발급하면 이전 초대는 무효다. 코드는 암호학적으로 무작위 생성하고 충돌 확인·서버 저장 시 해시 처리한다. 링크 로그에 원문 토큰을 남기지 않는다.

코드 확인은 계정·IP별 분당 최대 5회로 제한하고 로그인하지 않은 미리보기에는 방 이름·기간 초안·목표 초안·정원만 표시한다. 구성원 이름·출석·사진은 공개하지 않는다. 잘못된 코드, 만료된 코드, 비공개 방에 대해 정보를 과도하게 구별하지 않는 안내를 사용한다.

동시 참여 요청에서는 회차 잠금과 참가자 고유 제약으로 정원을 지킨다. 같은 사용자의 재입장은 중복 참가자를 만들지 않는다. 진행 중 신규 가입자는 현재 평가에 들어가지 않고 다음 회차 초대를 기다린다.

| 기본 공개 | 닉네임·날짜·인정 여부·완료 수·목표·결과 | 전원이 참가 전에 동의 |
| 중도 종료 | 기존 유효 기록 보존, 최종 상태는 중도 종료 | 목표 분모를 임의로 축소하지 않음 |
| 장애 처리 | 기술 오류 확인 시 정정·보류·무효 | 방장이 주관적으로 승인하지 않음 |
| 설명 | 최대 1,000자 | 참고 안내. 계산 규칙으로 실행하지 않음 |

기본 공개에 동의하지 않는 사람은 회차 참여를 확정할 수 없다. 사진 열람·세트 상세 열람·운동 시간 열람은 각각 선택 설정이다. 선택 설정을 거부해도 출석 조건을 충족하면 정상 평가한다.

자유서술 설명에 “월요일 필수”, “운동 1시간”, “스쿼트 100회”라고 적어도 서버가 평가하지 않는다. v1 화면에서는 지원하지 않는 평가 조건을 약속으로 표시하지 않도록 구조화된 규칙과 참고 설명을 명확히 구분한다.

### 5.4 게시·동의·수정

1. 방장이 룰북을 게시하면 `rulebook_version`과 `roster_version`을 생성한다.
2. 각 참가자는 시작·종료일, 목표, 인정 방식, 공개 범위, 중도 종료 정책을 확인하고 해당 버전에 동의한다. 방장도 동의한다.
3. 동의 화면에 비용이나 알림 수신을 묶지 않는다. 룰북 동의와 푸시 권한은 별개다.
4. 룰북을 바꾸거나 참가 명단이 달라지면 버전을 올리고 전원의 동의를 다시 받는다. 새 참가자에게 기록이 공유되기 때문이다.
5. 방장이 누구를 제외할 때는 당사자에게 알림함으로 사유를 전달한다. 제외 후 남은 명단에 다시 동의한다.
6. 개시 예약 전 참가자는 자유롭게 동의를 철회하거나 나갈 수 있다.

방장은 `동의 4/5명`과 미동의자를 확인한다. 체크박스를 대신 선택하거나 무응답을 동의로 처리할 수 없다.

룰북 작성·저장 후 `게시 완료`가 서버에 확정되면 참가 후보에게 새 버전 확인 알림을 생성한다. 임시 저장이나 파일 전송 성공만으로 알리지 않는다. 알림 대상·전달 수단·중복 억제는 12.6절을 따른다. 알림을 받거나 열어본 것은 룰북 동의를 의미하지 않는다.

## 6. 개시와 시간 경계

개시 버튼은 즉시 점수 누적을 시작하는 버튼이 아니라 합의된 시작일의 개시를 예약하는 버튼이다.

서버가 하나의 트랜잭션에서 다음을 확인한다.

1. 요청자가 현재 방장이고 참가자로 포함돼 있는가.
2. 참가 후보가 2~10명이며 전원이 최신 룰북·명단에 동의했는가.
3. 시작 시각이 현재보다 최소 1시간 뒤인 미래 날짜의 00:00인가.
4. 같은 방의 다른 회차와 운동 인정 기간이 겹치지 않는가.
5. 초대·명단·룰북을 잠그고 참가자·평가 구간·목표 스냅샷을 만들 수 있는가.

성공하면 `scheduled`로 전환하고 초대를 닫는다. 예약을 취소해 시작일·명단을 바꾸려면 `awaiting_consent`로 돌아가 새 버전 전원 동의를 받아야 한다. 예약 후 시작 전 한 명이 참여를 철회해도 같은 절차로 예약을 해제한다.

일정 작업이 `start_at`에 활성화한다. 작업 지연 시 API도 현재 시각을 기준으로 상태를 보정하므로 앱을 열지 않았다는 이유로 개시가 늦어지지 않는다. 실제 데이터 저장 시각은 UTC, 날짜 환산은 Asia/Seoul이다.

예: 시작 2026-10-05 00:00, 기간 14일이면 인정 범위는 `[2026-10-05 00:00, 2026-10-19 00:00)`이다.

- 1구간: 10월 5~11일, 마감은 10월 12일 00:00.
- 2구간: 10월 12~18일, 마감은 10월 19일 00:00.
- 정확히 마감 시각에 접수된 인증은 앞 구간에 포함하지 않는다.
- 전체 결과 정산 마감은 10월 20일 00:00이다.
- 10월 7일 수요일에 시작하면 10월 7~13일이 1구간이다. 기존 개인 주간 리포트와 범위가 다름을 표시한다.

## 7. 인증 및 기록 누적

### 7.1 참가자 경험

오늘 화면의 기존 인증·세트 기록을 이용한다. 사진을 제출하면 “개인 출석 저장 · 챌린지 A 반영 · 챌린지 B 반영”처럼 결과를 구분해 보여준다. 개인 출석 성공과 방 집계 성공을 같은 상태로 추정하지 않는다.

v1에서 한 사용자는 동시에 최대 3개 활성 회차에 참여할 수 있다. 개시 예약 시에도 겹치는 기간을 검사한다. 같은 운동이 조건을 충족하는 여러 방에 반영되는 것은 허용한다. 룰북에 이를 명시하며 방마다 다시 촬영하게 하지 않는다.

### 7.2 인정 조건

회차 출석은 다음 조건을 모두 만족할 때만 인정한다.

1. 해당 사용자가 고정 참가 명단에 있고 제출 당시 중도 종료·제재 상태가 아니다.
2. 완료 인증 이벤트가 회차 시작 이상, 종료 미만 시각에 서버에서 정상 접수되어 저장됐다.
3. 서버가 확정한 평가일이 해당 회차 구간 안에 있다.
4. 원천 기록이 본인 소유이며 완료 인증 이벤트와 연결된다.
5. 룰북의 인증 방식에 부합한다.
6. 같은 사용자·회차·평가일에 이미 인정된 출석이 없다.

| 입력 | 사진 필수 | 사진 또는 수동 |
| --- | --- | --- |
| 당일 사진 제출 성공 | 인정 | 인정 |
| 당일 수동 출석 완료 | 사진 보강 대기, 불인정 | 인정 |
| 운동 시작 버튼만 누름 | 불인정 | 불인정 |
| 세트·중량만 입력 | 불인정 | 불인정 |
| 휴식 표시 | 불인정, 독려 대상에서는 당일 제외 | 동일 |
| 과거 날짜에 세트 입력·수정 | 출석 소급 인정 없음 | 동일 |
| 마감 후 새 인증 제출 | 종료된 구간에 불인정 | 동일 |
| 네트워크 재전송으로 동일 제출이 반복됨 | 기존 처리 결과 반환, 추가 인정 없음 | 동일 |

### 7.3 인증 시각과 자정 처리

- `accepted_at`: 서버가 유효성을 검사하고 인증 수락 이벤트를 저장하는 트랜잭션 안에서 부여하는 시각. 실제 커밋이 성공해야 유효하다.
- `evaluation_date`: `accepted_at`을 Asia/Seoul 날짜로 환산한 값. 사용자가 보낸 날짜나 EXIF 시각을 신뢰해 바꾸지 않는다.
- 촬영 시각은 참고용이며 공식 마감 기준은 서버 접수다. 제출 버튼 옆에 “오늘 인정은 자정 전 서버 접수 완료 기준”을 표시한다.
- 업로드를 자정 전에 시작했어도 접수 기준 시각이 자정 이후면 전날 출석으로 인정하지 않는다. 현재 당일 업로드 API처럼 날짜가 바뀌면 재촬영을 안내한다.
- 오프라인 초안은 임시 자료이며 서버에 접수되기 전에는 방 출석이 아니다. 다음 날 복구된 초안으로 전날 출석을 소급 생성하지 않는다.
- 이미 서버에 저장됐으나 응답만 끊긴 요청은 같은 `submission_id`로 조회·재요청해 원래 `accepted_at`과 결과를 복원한다. 마감 후 재요청이 새 인증이 되는 것은 아니다.

이 기준은 오프라인 편의보다 일관된 판정을 우선한 v1 결정이다. 오프라인 촬영 보장 기능이 필요하면 별도 증빙 설계 후 변경한다.

### 7.4 수동 출석 후 사진 보강

현재 개인 수동 완료 뒤 사진 제출이 막히므로, 별도의 당일 사진 보강 동작을 추가한다.

- 원래 개인 세션 ID·개인 완료 시각을 보존한다.
- 당일 사진만 추가하고 새 사진 인증 이벤트·접수 시각을 기록한다.
- 사진 필수 회차에서는 사진 보강 접수 시점에 출석을 처음 인정한다.
- 수동 허용 회차에서는 기존 1회 인정을 유지하고 증빙 종류만 보강한다.
- 보강이 자정을 넘으면 전날 사진 필수 출석을 인정하지 않는다.
- 이미 정상 사진 인증이 있는 세션에는 추가 점수를 만들지 않는다.
- 당일 휴식 표시를 운동 완료로 바꾸는 복귀 경로도 명시적으로 제공한다. 과거 휴식은 방 출석으로 소급 전환하지 않는다.

### 7.5 원천 기록과 회차 기록의 관계

개인 운동 기록을 중복 생성하지 않는다. 개인 기록에 연결된 회차용 인정 원장과 평가 근거만 저장한다.

- 원장에는 회차·사용자·평가일·원천 세션 ID·인증 이벤트 ID·인증 방식·접수 시각·판정 사유·버전을 저장한다.
- 사진 파일 자체는 복제하지 않고 증빙 참조만 사용한다.
- 세트 수정은 출석 인정 횟수를 바꾸지 않는다. 선택 공개한 세트 요약만 정산 마감 전까지 갱신한다.
- 인증 철회나 오류 무효화는 원장 삭제 대신 상태 전환과 사유를 남겨 재계산한다.
- 개인 사진 공유를 끄는 것은 증빙 접근 철회다. 사진을 남에게 숨겼다는 이유로 이미 인정된 출석을 취소하지 않는다.
- 사용자 데이터 삭제가 발생하면 사진·개인 식별정보를 접근 차단·정리하고, 필요한 최소 익명 집계와 정정 이력을 구분해 처리한다. 영구 보관을 기본으로 두지 않는다.

### 7.6 운동 소요 시간 측정

#### 측정 범위와 사용자 동작

운동 소요 시간은 사용자가 `운동 시작`부터 `운동 종료`까지 켜둔 타이머의 누적 시간이다. 센서로 실제 운동 동작을 검증한 시간이 아니다. 웜업·세트 사이 휴식은 포함하고 사용자가 명시적으로 누른 일시정지 구간은 제외한다.

- 기존 `지금 출발`은 이동을 시작한다는 의미를 유지하고 타이머를 자동 시작하지 않는다.
- 운동 화면에 별도 `운동 시작`을 두고, 출발 단계를 거치지 않아도 사용할 수 있게 한다.
- 측정 중에는 `일시정지`, `운동 종료`, 정지 중에는 `재개`, `운동 종료`를 표시한다.
- 종료하면 측정 시간을 저장한 뒤 아직 출석하지 않은 경우 기존 사진·수동 인증으로 이어간다. 종료 자체가 출석 인증은 아니다.
- 사진·수동 인증을 타이머보다 먼저 해도 된다. 인증이 타이머를 몰래 종료하지 않으며, 측정 중이면 본인에게 종료 여부를 별도로 안내한다.
- 타이머 없이 바로 인증할 수 있다. 이 경우 출석은 정상 판정하고 시간은 `미측정`으로 표시한다.
- 하루 여러 번 운동하면 각각의 종료된 타이머를 합산하되 출석은 하루 최대 1일이다.

타이머와 기존 개인 출석 상태는 독립적이다. 개인 출석이 `completed`여도 같은 날 두 번째 운동 타이머를 시작할 수 있다. 방장에게 타이머를 원격 시작·종료·수정하는 권한은 주지 않는다.

#### 상태·계산·예시

| 상태 | 의미 | 허용 동작 |
| --- | --- | --- |
| `running` | 열린 측정 구간 1개가 있음 | 일시정지, 종료 |
| `paused` | 열린 구간 없음, 누적 시간 보존 | 재개, 종료 |
| `finished` | 종료 시각·누적 시간 확정 | 본인 보정·제외, 이력 열람 |
| `needs_review` | 종료 누락·시각 충돌 등으로 확인 필요 | 본인 보정 또는 기록 제외 |
| `discarded` | 사용자가 잘못 시작한 측정을 제외 | 이력만 보존, 합계에서 제외 |

사용자당 `running` 또는 `paused` 타이머는 전체 기기를 합쳐 최대 1개다. `needs_review`는 활성 타이머에서 해제하되 해결 전까지 정상 합계에 포함하지 않는다. 다른 기기에서 열면 서버 상태를 복원하며 동시 명령은 `revision`으로 충돌을 검사한다.

```text
measured_seconds = sum(segment_ended_at - segment_started_at)
표시 합계 분 = floor(모든 유효 구간의 합계 초 / 60)
```

저장은 초 단위, 측정 중 화면은 `시:분:초`, 리포트는 시간·분을 표시한다. 각 구간을 먼저 분으로 잘라 합산하지 않는다. 일시정지 상태에서 종료하면 마지막 종료 명령까지의 대기 시간은 더하지 않는다.

예: 19:00 시작 → 19:30 일시정지 → 19:40 재개 → 20:10 종료면 경과 시간 70분, 운동 소요 시간 60분이다. 20:20에 사진을 올려도 10분이 더해지지 않는다.

#### 화면 꺼짐·네트워크·종료 누락

- 서버에 저장한 시작·정지·종료 시각으로 계산한다. 매초 DB를 갱신하거나 JavaScript 타이머 실행 횟수를 누적하지 않는다. 화면의 초 표시는 서버 기준 시각과의 차이로 보간한다.
- 화면 꺼짐·다른 앱 사용·정상 앱 종료는 자동 일시정지로 취급하지 않는다. 다시 열면 서버의 마지막 상태와 경과 시간을 복원한다.
- v1의 신규 시작·재개는 서버 접수가 성공해야 확정한다. 오프라인 상태에서는 새 측정을 정상 시작한 것처럼 표시하지 않는다.
- 측정 도중 연결이 끊기면 로컬 화면은 계속 경과 시간을 표시한다. 일시정지·종료를 누르면 화면은 즉시 멈추고 해당 명령을 `동기화 대기`로 보관한다.
- 늦게 도착한 종료 명령의 서버 수신 시각까지 운동했다고 계산하지 않는다. 원래 입력 시각·순서·누적값을 검증해 사용자 기록으로 분류하고 원본 서버 측정 구간과 구분한다.
- 온라인 명령만으로 확정한 기록은 `timer_recorded`, 오프라인 종료·시각 보정이 들어간 기록은 `self_reported`로 표시한다. 두 합계를 합쳐 검증된 측정값처럼 보여주지 않는다.
- 재부팅·기기 시각 변경·다른 기기의 명령으로 순서나 시각을 확인할 수 없으면 `needs_review`로 돌린다. 사용자에게 실제 소요 시간을 확인받고 `self_reported`로 저장하거나 제외한다.
- 세션 만료 중에도 로컬 종료 의도는 사용자별로 보존한다. 재로그인 후 서버 버전을 확인해 복구하며 다른 계정에 연결하지 않는다.
- 같은 `request_id`의 재시도는 같은 상태를 반환한다. 상태 충돌 시 로컬 종료 의도를 버리거나 조용히 덮어쓰지 않고 확인을 요청한다.
- 타이머 생성 후 6시간 안에 종료하지 않으면 종료 누락 확인 상태로 전환한다. 6시간을 정상 운동 시간으로 자동 적립하지 않는다. 6시간은 v1 제품 기본값이며 실제 운동 제한을 의미하지 않는다.
- 본인 보정은 이유와 변경 전후를 기록하고 `self_reported`로 분류한다. 과거 기록에 시간을 입력해도 출석 인증 이벤트가 생기지 않는다.

#### 날짜·회차·출석과의 연결

타이머는 개인 출석 세션과 별도로 저장하고 구간을 사용자 시간대의 자정 기준으로 분할해 일별 시간을 만든다. 예를 들어 23:30~00:20은 첫날 30분, 다음 날 20분이다. 개인 기록에는 두 날짜의 시간을 보여주되 새 출석을 자동 생성하지 않는다.

방의 시간 요약은 다음 조건으로 생성한다.

1. 해당 참가자가 시간 공유에 동의한 회차만 대상으로 한다.
2. 회차 시작 이상·종료 미만의 시간과 실제 참가 중인 시간에 겹치는 측정 구간만 포함한다.
3. 방에서 유효 출석이 인정된 날짜의 구간만 방의 출석 연계 시간 합계에 포함한다. 출석 없이 측정된 시간은 본인 개인 기록에 남는다.
4. 종료된 정상 타이머와 확인된 사용자 기록을 종류별로 분리해 집계한다. 진행 중·확인 필요·폐기 기록은 합계에서 제외한다.
5. 회차 정산 마감 전 확정된 측정·보정만 해당 결과 스냅샷에 포함한다. 회차 밖 시간은 나중에 종료해도 포함하지 않는다.
6. 정산 후 개인 시간을 수정해도 확정된 방 결과의 시간 요약은 바뀌지 않는다. 공유 철회 시 다른 사람의 열람은 차단한다.

따라서 자정을 넘긴 운동은 날짜별 출석도 별도로 충족해야 방의 두 날짜에 시간이 반영된다. 타이머의 전날 구간이 남아 있어도 전날 출석 마감은 연장되지 않는다. 미측정·확인 필요를 0분으로 처리하지 않으며, “출석 3일 중 시간 측정 2일”처럼 자료 범위를 표시한다.

시간은 현재 회차의 성패·순위·최소 운동 시간 조건에 사용하지 않는다. 시간에 따른 인정 규칙은 사용자가 별도로 요청할 경우 룰북 버전과 동의 체계를 확장한다.

## 8. 운동 진행 결과와 데이터 공개

### 8.1 방장에게 기본 제공하는 지표

- 구간별 인정 출석 `2/3일`, 달성률, 남은 목표.
- 마지막 인정일, 사진·수동 등 인증 종류, 현재 구간 상태.
- 달성한 구간 수, 전체 기간의 출석 합계, 중도 종료 여부.
- 오늘 휴식 표시 여부. 개인적인 휴식 사유는 공개하지 않는다.
- 전체 참가자 중 목표를 달성한 사람 수.

`운동 시작` 이벤트는 실제 운동 중임을 보장하지 않으므로 기본 방 화면에 “운동 중”으로 표시하지 않는다. 인증이 없으면 “오늘 인증 없음”으로 표시하고 “운동 안 함”으로 단정하지 않는다.

### 8.2 선택 공개

| 데이터 | 기본 | 선택 공유 시 |
| --- | --- | --- |
| 사진 존재·인증 종류 | 동일 회차 참가자에게 공개 | 사진 자체는 아래 별도 권한 |
| 인증 사진 | 본인만 | 회차별로 방장에게만 공개 가능 |
| 종목·세트·중량·반복 수 | 본인만 | 회차별로 방장에게 상세 공개 가능 |
| 운동 소요 시간 | 본인만 | 회차별로 방장에게 일별·구간별 합계, 측정/사용자 기록 구분, 측정일 수 공개 가능 |
| 운동 메모·체중·과거 개인 리포트 | 본인만 | v1 공유 대상 아님 |
| 다른 방 이름·구성원·성적 | 비공개 | v1 공유 대상 아님 |
| 연락처·이메일·기기 토큰 | 비공개 | 방장 열람 불가 |

사진·상세 기록·운동 시간의 공개 동의는 회차와 방장 계정에 묶는다. 방장이 바뀌면 선택 공개는 기본 비공개로 돌아가며 새 방장에게 다시 동의해야 한다. 출석 요약에 대한 회차 참가자 간 공개는 유지한다.

출석 공유를 철회하고 싶은 참가자는 회차 중도 종료 후 방을 나갈 수 있다. 이후 새 기록은 공유하지 않으며 기존 집계에는 익명화된 중도 종료 상태를 남긴다. 선택 공개는 참여를 유지한 채 언제든 철회할 수 있다.

방장은 회차 기간의 데이터만 볼 수 있다. 상세 운동 향상 비교도 회차 안의 동일 종목·동일 중량 반복 수, 또는 동일 반복 수의 중량 변화처럼 비교 조건이 성립할 때만 표시한다. 데이터가 적으면 “비교 자료 부족”이다. 다른 사람끼리 중량을 비교해 순위를 매기지 않는다.

운동 소요 시간은 7.6절의 별도 타이머로 추가한다. 기존 `started_at`부터 `completed_at`까지의 차이는 이동·인증 지연을 포함하므로 사용하지 않는다. 방장은 공개 동의가 있는 종료된 기록의 합계·종류·측정 범위를 확인하며, 타이머가 켜져 있다는 이유로 참가자의 현재 행동을 추정하거나 실시간 감시 화면을 제공하지 않는다.

### 8.3 조회 보안과 보관

서버는 모든 조회마다 요청자의 회차 참여, 방장 역할, 공유 동의, 대상 기록의 기간을 확인한다. 상대의 사용자 ID를 받아 기존 본인용 API의 소유권 검사를 우회하지 않는다.

- 선택 공유한 사진·세트·운동 시간은 해당 회차 정산 종료 후 30일까지 방장 열람을 기본으로 한다. 동의 철회·탈퇴·제재 시 즉시 차단한다.
- 평가 근거·집계·운영 이력은 기본 1년 보관 후 최소 익명 통계로 정리하는 제품 기준안으로 둔다. 개인 기록 자체의 보관 정책과 분리한다.
- 공개 범위를 확대하는 변경은 새 동의를 받는다. 종료 결과 공유 이미지는 개인이 자신의 결과를 선택해 공유하며 다른 사람의 이름·사진을 넣지 않는다.
- 저장 API 응답에도 불필요한 사진 경로·원본 파일 키·개인 메모가 포함되지 않아야 한다.

## 9. 평가 시스템

### 9.1 평가 변수와 공식

사용자별, 7일 구간별로 다음을 계산한다.

```text
target_count = 룰북에 고정된 구간 목표
completed_count = 구간 안의 유효한 서로 다른 evaluation_date 개수
credited_count = min(completed_count, target_count)
remaining_count = max(target_count - completed_count, 0)
achievement_percent = min(100, round_half_up(100 × completed_count / target_count))
extra_count = max(completed_count - target_count, 0)
```

표시 퍼센트는 정수 반올림하되, 달성 여부는 반올림된 값이 아닌 실제 정수 횟수 비교로 결정한다. `target_count`는 1 이상이므로 0으로 나누는 경우를 허용하지 않는다.

전체 회차 진행률은 `sum(credited_count) / sum(target_count) × 100`이다. 초과 운동을 다음 구간에 이월하지 않는다. 주간 목표 3일인 14일 회차에서 1구간 5일·2구간 1일이면 원시 출석 합계는 6일이어도 평가 진도는 4/6, 67%이고 최종 미달이다.

### 9.2 진행 상태

| 조건 | 표시 | 설명 |
| --- | --- | --- |
| 구간 시작 전 | 시작 대기 | 분모만 준비, 독려 불가 |
| 진행 중이고 목표 충족 | 목표 충족·잠정 | 기간 종료 전까지 정정 가능 |
| 진행 중이고 목표 미충족 | 진행 중 | 미래의 예정일을 결석으로 세지 않음 |
| 남은 인정 가능한 날짜 수 = 남은 목표 | 남은 날 모두 인증 필요 | 오늘 인정이 없으면 오늘도 가능한 날짜에 포함 |
| 남은 인정 가능한 날짜 수 < 남은 목표 | 이번 구간 목표 달성 어려움 | 달성을 위해 하루 여러 번 운동하라고 유도하지 않음 |
| 구간 종료, 정산 전 | 달성·미달 잠정 | 서버 검산·오류 접수 대기 |
| 중도 종료 | 중도 종료 | 목표 충족 여부와 별도 상태 |

“오늘 인증 없음”을 즉시 “위험”으로 표시하지 않는다. 개인 운동 예정 시간이 지나지 않았거나 오늘 휴식인 경우 재촉 추천에서 제외한다.

### 9.3 구간 마감과 최종 정산

1. 구간이 끝나면 해당 구간의 신규 인증을 차단하고 잠정 결과를 만든다.
2. 14·28일 회차의 다음 구간은 원래 일정대로 시작한다. 이전 구간에서 미달해도 계속 참여할 수 있다.
3. 전체 회차 종료 후 24시간 동안 이미 접수된 이벤트 누락·중복 등 기술 오류 이의를 받는다. 새 운동이나 늦은 사진을 추가하는 유예 시간이 아니다.
4. 서버가 원천 이벤트와 원장, 대상자, 룰북 버전, 정정 이력을 대조한다.
5. 해결되지 않은 기술 오류가 있으면 `review_required`로 남기고 예상 결과를 확정값으로 표시하지 않는다. 연관 없는 회차는 계속 처리한다.
6. 검산이 완료되면 `evaluation_version`, 근거 범위, 정산 기준 시각을 포함한 결과 스냅샷을 원자적으로 저장한다.
7. 최종 결과 알림을 남긴다. 이후 개인 기록을 수정해도 확정된 출석 결과는 자동으로 바뀌지 않는다.

정산 마감 전에는 방에서 공유한 세트·운동 시간 요약이 변경될 수 있음을 표시한다. 정산 후 결과에 포함된 요약은 해당 버전의 스냅샷이다. 과거 개인 기록의 실시간 리포트와 다른 값일 수 있다. 시간 미측정·확인 필요는 출석 판정의 기술 오류가 아니므로 이것만으로 전체 회차 정산을 보류하지 않는다.

### 9.4 결과 상태와 집계 분모

| 결과 | 조건 |
| --- | --- |
| `achieved` | 기간을 끝까지 참여하고 모든 구간 목표를 달성 |
| `missed` | 기간을 끝까지 참여했으나 한 구간 이상 미달 |
| `withdrawn` | 사용자가 중도 종료. 그때까지 기록은 남기되 성공으로 세지 않음 |
| `removed` | 운영 제재로 참여 종료. 미달·부정 인증 판정과 혼동하지 않음 |
| `voided` | 회차 전체 평가 무효. 성공률 계산에서 제외 |

방의 최종 달성자 비율은 `achieved 인원 / 시작 시 확정된 참가자 수`로 계산한다. 중도 종료·제재자가 나가도 분모를 줄이지 않는다. 달성자·미달자·중도 종료·제재 종료를 함께 표시해 숫자만으로 오해하지 않게 한다.

동률을 깨는 기준이나 단독 우승자는 없다. 목표를 채운 사람은 모두 달성자다. 초과 운동은 참고값이며 우열·상금·추가 점수로 연결하지 않는다.

### 9.5 실제 운동 진위와 이의 제기

v1 자동 검사는 제출 시각, 소유권, 형식, 정확히 같은 이미지 중복, 중복 요청만 판정한다. 사진 한 장으로 실제 운동 사실을 보장하지 않는다. 수동 허용 회차는 자기 신고 기반이라는 표시를 유지한다.

- 방장과 참가자는 인증에 대해 신고할 수 있지만 상대 출석을 직접 무효화할 수 없다.
- 단순한 의심·다수결로 점수를 깎지 않는다. v1에 사람이 사진 내용을 심사하는 경쟁 판정 기능을 넣지 않는다.
- 운영자는 서버 증거로 확인되는 누락·중복·시스템 오류를 정정한다. 정정 전후, 사유, 담당자, 결과 버전을 남긴다.
- 괴롭힘·부적절한 사진은 접근 차단·제재 대상으로 처리하며 운동 진위 판정과 분리한다.
- 확정 후 기술 오류가 확인되면 이전 결과를 지우지 않고 새 결과 버전을 발행한다. 전체 참가자에게 변경 이유를 알린다.

### 9.6 계산 예시: 4명·14일·구간당 3일

아래 숫자는 실제 사용자 데이터가 아닌 검산용 예시다.

| 참가자 | 1구간 출석 | 2구간 출석 | 목표에 반영되는 횟수 | 전체 진행률 | 최종 상태 |
| --- | --- | --- | --- | --- | --- |
| A | 3 | 3 | 6/6 | 100% | 달성 |
| B | 5 | 1 | 4/6 | 67% | 미달 |
| C | 3 | 3 | 6/6 | 100% | 달성 |
| D | 1 | 0 | 1/6 | 17% | 중도 종료 |

- 방의 실제 인정 출석 합계는 19일이다. 여러 사람의 출석을 합친 값이며 달력상의 19일이라는 뜻은 아니다.
- 목표 충족 진행률은 17/24, 71%다. B의 1구간 초과 2일은 다른 구간의 부족분을 메우지 않는다.
- 최종 달성자 비율은 2/4, 50%다. D가 나갔다고 2/3으로 바꾸지 않는다.
- D에게 남은 목표를 강제로 채우게 하지 않는다. 기록상 상태만 중도 종료로 남긴다.
- B가 다음 회차에서 성공해도 이전 미달 결과는 바뀌지 않는다.
- 화면에서 `목표 충족 진행률`과 `달성자 비율`을 같은 이름의 “출석률”로 표시하지 않는다.

## 10. 결과 화면

개인 결과에는 기간, 룰북 요약, 구간별 출석/목표, 인정 날짜, 전체 달성 여부, 평가 기준 버전을 제공한다. 불인정 기록이 있으면 사유를 본인이 확인할 수 있다.

방장 결과에는 다음을 표시한다.

- 시작 인원, 끝까지 참여한 인원, 달성·미달·중도 종료·제재 종료 인원.
- 각 참가자의 구간별 목표 달성 결과와 전체 판정.
- 공유에 동의한 참가자의 출석 연계 운동 시간·사용자 기록 시간·시간 측정일 수. 미공개와 미측정은 별도 표시.
- 전체 유효 출석일 합계와 초과 출석을 제외한 목표 충족 진행률.
- `같은 멤버로 다음 회차`, `내 결과 공유`, `룰북·평가 근거 보기`.

진행 중 화면과 결과 화면의 계산식을 다르게 만들지 않는다. 프런트엔드는 서버에서 계산한 값과 버전을 표시하며 자체 점수를 재계산하지 않는다.

## 11. 기존 인원으로 기간 연장·재도전

사용자 화면에서는 “기간 연장” 대신 “같은 멤버로 이어하기”를 주 동작으로 쓴다. 안내에는 “현재 회차는 예정대로 종료하고 새 회차를 시작합니다”를 표시한다.

1. 방장은 현재 회차 마지막 3일 또는 종료 후 다음 회차를 제안할 수 있다.
2. 기존 룰북을 새 초안으로 복사하고 다음 시작일·기간·목표를 지정한다. 원 회차의 목표·마감·결과는 수정하지 않는다.
3. 현재 방에 남아 있는 기존 참가자에게 제안 알림을 보낸다. 탈퇴·차단·제재된 사용자를 자동 재초대하지 않는다.
4. 기존 인원은 기본 후보일 뿐 자동 참가자가 아니다. 각자 룰북과 명단에 다시 동의한다.
5. 새 회차 시작 1시간 전까지 확정 참가자가 2명 이상이고 전원 최신 버전에 동의하면 방장이 개시를 예약한다.
6. 거절·미응답자는 참가자로 확정하지 않는다. 명단에서 제외하면 남은 참가자에게 바뀐 명단을 다시 확인받는다.
7. 기한까지 준비되지 않으면 자동으로 기간을 옮기지 않고 시작일을 다시 제안해 동의를 받는다.

예: 1회차 10월 5~11일 → 2회차 10월 12~18일. 1회차 정산은 10월 12일 하루 동안 진행할 수 있고, 2회차 출석은 12일부터 따로 쌓인다. 1회차 미달은 2회차 운동으로 바뀌지 않는다.

기존 출석 요약 공개 동의도 새 회차에서 다시 확인한다. 사진·세트·운동 시간의 선택 공유는 복사하지 않고 기본 비공개로 시작한다. 알림 수신 선호는 사용자 설정을 유지하되 동의 화면에서 변경 가능하다.

새 멤버 추가는 다음 회차 명단 확정 전까지 허용한다. 진행 중 회차에 소급 편입하지 않는다. 방의 누적 화면에는 회차별 결과를 나란히 보여주고, 서로 다른 목표 회차를 하나의 점수로 합쳐 순위를 만들지 않는다.

## 12. 방장 재촉·원격 푸시·알림함

### 12.1 기능과 문구

방장은 개인별 `재촉하기` 또는 `가능한 참가자에게 한 번 보내기`를 누른다. 기본 템플릿은 “이번 운동 약속을 확인해 주세요”이며 앱 안에서는 해당 방과 남은 목표를 자세히 보여준다.

자유 입력 푸시와 참가자끼리 재촉은 v1에 포함하지 않는다. 다른 사람의 운동 성적·실명·사진을 잠금 화면에 노출하지 않는 기본 문구를 사용한다. 개인 알림의 매운맛 설정이 방장 알림에 자동 적용되지는 않는다.

### 12.2 대상 선정과 제한

아래 수치는 v1 운영 기본값이다. 서버 설정으로 관리하되 이미 동의한 회차에서 더 공격적으로 변경하지 않는다.

| 조건 | 처리 |
| --- | --- |
| 요청자 | 현재 방장만 가능. 자신의 계정은 대상에서 제외 |
| 회차 | `active`에서만 재촉 가능 |
| 목표 | 현재 7일 구간 목표가 남은 사람만 |
| 당일 상태 | 오늘 인정 출석 또는 휴식 표시가 있으면 제외 |
| 예정 시간 | 개인 운동 예정 시각 +30분 이후. 요일과 무관하게 공통 시간 기준 사용 |
| 달성 가능성 | 남은 날짜로 목표 달성이 불가능해진 구간은 수동 재촉에서 제외 |
| 푸시 대상 | 앱 알림 권한이 켜져 있고 활성 푸시 기기가 등록된 참가자. 방별 재촉 수신 동의를 요구하지 않음 |
| 방별 빈도 | 수신자당 하루 1건 |
| 전체 빈도 | 모든 방 합쳐 수신자당 하루 최대 2건, 이전 방장 재촉 후 4시간 간격 |
| 요청자 빈도 | 방장당 분당 5회 요청 제한, 반복 누름은 동일 요청으로 처리 |
| 허용 시간 | 수신자 설정 시간대 기준 09:00~21:00. 기본 Asia/Seoul |
| 방해 금지 시간 | 서버가 대기열 등록과 발송 직전에 검사하고 다음 허용 시간까지 발송을 연기 |
| 토큰·권한 없음 | 앱 알림함에만 기록. “휴대폰 푸시 발송”이라고 표시하지 않음 |

개인 목표가 남았다는 이유만으로 매일 방장이 재촉할 수 있게 만들지 않는다. 당일 출석, 휴식, 예정 시각을 함께 확인한다. 휴식 표시는 점수를 올려주지 않고 당일 재촉만 막는다.

개인 로컬 운동 알림 설정은 서버 재촉의 발송 조건에 영향을 주지 않는다. 서버 재촉은 앱 알림 권한과 서버 방해 금지 시간에 따른다. v1은 기기 로컬 알림의 실제 표시 시각까지 완전히 통합해 중복을 차단한다고 약속하지 않는다.

### 12.3 처리 흐름

1. 방장 앱이 회차·선택 대상 또는 전체 대상 의도와 `request_id`를 서버에 보낸다.
2. 서버가 방장 자격·회차 상태·대상 소속·최신 출석·빈도를 다시 확인한다.
3. 적격 수신자별 재촉 이벤트와 발송 대기 항목을 트랜잭션으로 저장한다. 같은 요청의 재전송은 같은 처리 결과를 반환한다.
4. 발송 작업자가 발송 직전에 활성 기기와 서버 방해 금지 시간을 다시 확인한다. 방해 금지 시간이면 다음 허용 시간까지 발송을 미룬다.
5. 허용 시 앱 알림함을 만들고 사용자의 활성 기기로 원격 푸시를 요청한다. 복수 기기에 전달돼도 재촉 1건으로 계산한다.
6. 푸시를 누르면 로그인·참여 권한을 검증한 뒤 해당 방으로 이동한다. 이미 종료된 회차면 결과 화면을 연다.

DB 저장과 푸시 서비스 요청을 같은 원자적 처리로 볼 수 없으므로 발송 대기열(outbox)을 사용한다. 외부 발송 실패가 운동 기록 저장·방 조회를 막으면 안 된다.

알림 상태는 `queued`, `provider_accepted`, `failed`, `cancelled`로 구분한다. `provider_accepted`는 푸시 서비스가 요청을 접수했다는 의미이며 사용자가 봤다는 뜻이 아니다. 방장에게 읽음·열람 시각을 제공하지 않는다.

모든 대상이 제외되면 “지금 재촉할 수 있는 참가자가 없습니다”로 끝낸다. 일괄 발송 후에는 “알림 요청 2건 접수”처럼 확인 가능한 결과만 표시한다. 기기 권한 상태를 방장에게 노출하지 않는다.

### 12.4 추가 인프라와 수명주기

- Android 원격 푸시는 FCM, iOS는 APNs 연동이 필요하다. iOS를 FCM을 통해 보낼지 APNs로 직접 보낼지는 실제 플러그인의 토큰 형태에 맞춰 구현 시 확정한다.
- 기존 Capacitor 7과 호환되는 푸시 플러그인, 플랫폼 설정·서버 자격증명·실기기 검증을 추가한다. APNs 토큰을 FCM 토큰으로 취급하지 않는다.
- 로그인한 기기의 토큰을 사용자와 연결하고 토큰 갱신·계정 전환·기기별 중복을 처리한다. 서버 발송 자격증명은 앱에 넣지 않는다.
- 명시적 로그아웃과 계정 전환 시 토큰 연결을 해제한다. 현재 전체 기기 로그아웃은 서버의 해당 사용자 기기 연결도 모두 해제한다.
- 세션 만료 자체는 로그아웃 의사로 보지 않는다. 활성 기기에 일반 안내 푸시는 받을 수 있지만 상세 화면은 재로그인 후 접근한다.
- 서버에 없는 로컬 로그아웃으로 끝난 경우도 기기 토큰 해제를 별도로 시도하고 실패 상태를 추적한다. 오래된 토큰은 공급자 오류·갱신 실패 정책으로 비활성화한다.
- 재시도는 최초 시도 후 최대 2회. 30초·2분 뒤 시도하되 유효시간 내에서만 한다. 영구 실패 토큰에는 재시도하지 않는다.
- 동일 알림 ID·플랫폼 중복 억제 기능으로 재전송 표시를 줄이되 정확히 한 번 표시를 보장하지 않는다.
- 푸시 성공·실패와 상관없이 서버 알림함이 앱에서 확인할 근거다. 알림함은 기본 90일 보관하며 운동 결과는 별도 저장한다.

### 12.5 시스템 알림 종류

| 사건 | 대상 | 알림함 | 원격 푸시 |
| --- | --- | --- | --- |
| 룰북 공식 게시·변경 | 방장을 제외한 현재 참가 후보 | 필수 기록 | 활성 기기에 기본 발송, 상세 정책은 12.6절 |
| 개시 예약·예약 취소 | 해당 참가자 | 필수 기록 | 활성 기기에 기본 발송 |
| 회차 시작 | 확정 참가자 | 기록 | 활성 기기에 기본 발송 |
| 방장 재촉 | 적격 대상 | 기록 | 활성 기기에 기본 발송 |
| 최종 결과·정정 | 해당 회차 참가자 | 필수 기록 | 활성 기기에 기본 발송 |
| 다음 회차 제안 | 남아 있는 기존 구성원 | 기록 | 활성 기기에 기본 발송 |
| 방장 양도 요청·완료 | 지명자·기존 구성원 | 기록 | 활성 기기에 기본 발송 |

참가자 매 인증마다 모든 사람에게 푸시를 보내지 않는다. 전체 출석 현황은 방 화면에서 갱신한다. 가입 동의나 결과 확인에 푸시 허용을 필수로 요구하지 않는다.

### 12.6 룰북 업로드·게시 완료 알림: 가능 여부와 채택 방식

확인 결론: 참가자 앱이 꺼져 있을 때 새 룰북 게시 사실을 알리려면 원격 푸시가 필요하다. 로컬 알림만으로 방장의 서버 변경을 다른 기기가 즉시 감지할 수는 없다. 현재 코드의 `LocalNotifications`는 각 기기가 이미 알고 있는 일정의 알림을 예약하는 용도다. [Capacitor 7 로컬 알림](https://capacitorjs.com/docs/v7/apis/local-notifications), [Apple 원격 알림 구조](https://developer.apple.com/documentation/usernotifications/setting-up-a-remote-notification-server)

| 참가자 상태 | 로컬 알림만 사용할 때 | v1 채택 방식 |
| --- | --- | --- |
| 방 화면이 열려 있음 | 서버를 조회해 게시를 발견한 뒤 기기가 표시 가능 | 새 룰북 배너·동의 상태 갱신 |
| 다른 앱 화면 또는 백그라운드 | 새 서버 이벤트의 즉시 감지를 보장하지 못함 | 원격 푸시 요청, 서버 알림함 기록 |
| 앱 종료 | 미리 예약한 알림은 가능하지만 새 게시 사건을 알 수 없음 | 원격 푸시 요청. OS·기기 상태에 따라 지연·미전달 가능 |
| 알림 권한 거부·오프라인 | 게시 즉시 표시를 보장하지 못함 | 알림함 보존, 다음 접속 때 최신 룰북 표시 |
| 앱 미설치·대기실 미참여 | 대상 기기·참가자 연결 없음 | 자동 푸시 대상 아님. 초대 링크에서 최신 룰북 확인 |

표의 앱 종료는 원격 알림 도입의 필요성을 뜻하며 모든 강제 종료·절전 상태에서 도착을 보장한다는 뜻은 아니다. 무음 푸시로 앱을 깨워 로컬 알림을 만드는 방식을 필수 경로로 삼지 않는다. 원격 푸시를 도입하기 전에는 `알림함 저장·접속 시 확인`까지만 제공하고 “참가자 휴대폰에 알림 전송 완료”라고 표시하지 않는다.

#### 발행 사건과 대상

- 본 문서에서 “업로드 완료”는 구조화된 룰북의 검증·버전 저장·공식 게시가 서버에서 성공한 시점이다. PDF·사진 첨부 업로드는 현재 범위에 없으며, 추가하더라도 첨부 전송 성공만으로 룰북을 게시하거나 동의 대상을 변경하지 않는다.
- 룰북 게시 트랜잭션에서 `rulebook_published` 사건과 수신 대상, 알림함 항목, 원격 발송 outbox를 함께 저장한다. 푸시가 실패해도 게시 자체는 유지한다.
- 대상은 게시 시점에 해당 대기실에 들어와 있는 참가 후보이며 아직 룰북에 동의하지 않은 사람도 포함한다. 게시자인 방장과 탈퇴·제외된 사람은 제외한다.
- 게시 후 새로 들어온 참가자는 즉시 최신 룰북과 `동의 필요`를 보여준다. 과거 게시 알림을 몰아서 보내지 않는다.
- 방장은 게시 성공과 알림 요청 접수 결과를 확인할 수 있다. 참가자의 푸시 허용 여부·열람 시각은 공개하지 않는다.

#### 전달·중복·최신 버전 처리

- 기본 문구는 “참여 중인 챌린지의 룰북이 게시되었습니다. 내용을 확인하고 동의해 주세요.”다. 변경 게시에는 “룰북이 변경되었습니다. 다시 확인해 주세요.”를 사용한다.
- 방 소식과 방장 재촉은 방별 수신 스위치 없이 활성 기기에 기본 발송한다. 게시 알림은 재촉 한도를 사용하지 않는다.
- 각 `(round_id, rulebook_version, recipient_user_id)`에 알림 사건을 한 번만 만든다. 같은 게시 요청을 재시도해도 새 알림을 생성하지 않는다.
- 공식 게시 API는 회차당 5분 간격을 둔다. 초안 저장은 가능하다. 아직 발송하지 않은 이전 버전 푸시는 최신 버전으로 대체해 연속 수정 알림을 줄인다.
- 서버는 수신자의 방해 금지 시간을 대기열 등록 시점과 실제 발송 직전에 확인한다. 기본 허용 시간은 수신자 시간대 기준 09:00~21:00이다. 게시 알림과 재촉의 발송 한도는 별도로 관리한다.
- 발송 직전 탈퇴·취소·새 버전·이미 최신 버전에 동의했는지 검사한다. 불필요한 발송은 취소하되 과거 게시 이력과 알림함은 유지한다.
- 원격 메시지에 `notification_id`, `round_uuid`, `rulebook_version`, `event_type`을 넣고, 클릭 시 최신 접근 권한·버전을 조회한다. 오래된 알림을 눌러도 구버전에 동의시킬 수 없다.
- 같은 사건을 원격 푸시와 별도 로컬 알림으로 중복 표시하지 않는다. 포그라운드에서는 앱 배너·알림함을 사용하고, 백그라운드의 OS 표시와 분리한다.
- 룰북 게시를 로컬 알림으로만 실험하는 중간 버전에서는 서버 조회 후 배너만 표시해도 충분하다. 해당 방식은 앱 종료 시 원격 알림의 대안이 아니다.

기술 적용은 프로젝트 버전에 맞는 [Capacitor 7 Push Notifications](https://capacitorjs.com/docs/v7/apis/push-notifications)를 기준으로 한다. Android의 FCM 등록, iOS의 APNs 권한·등록, 기기 토큰 서버 연결은 12.4절의 원격 알림 도입 범위에 포함한다.

## 13. 기타 운영 기능과 예외

### 13.1 중도 종료·부상·질병

앞선 논의의 “면제권 1회”는 v1 기본안에서 제외한다. 출석 1회를 인정하는지, 목표를 줄이는지, 구간을 제외하는지에 따라 결과가 달라지기 때문이다.

대신 누구나 강요 없이 중도 종료할 수 있다. 부상·질병을 증명하는 자료는 요구하지 않는다. 결과는 중도 종료로 구분하고 별도 벌칙을 부과하지 않는다. 휴식을 선택해도 룰북 목표는 줄어들지 않으며, 다음 회차에서 낮은 목표를 다시 합의할 수 있다.

### 13.2 방장 양도·부재

- 현재 방장이 같은 회차의 정상 참가자에게 제안하고 24시간 안에 수락하면 양도한다.
- 수락 시 현재 역할·대상 상태를 재확인한다. 요청 중 역할이 이미 변경됐으면 실패한다.
- 진행 중 방장은 양도 후 참여를 종료할 수 있다. 자신의 요청을 타인 대신 수락할 수 없다.
- 계정 삭제·운영 정지로 방장이 사라지면 `host_vacant` 표시를 두고 자동 집계·정산은 계속한다. 재촉·룰북 수정·후속 회차 개시는 막는다.
- 남은 정상 참가자 모두가 후보 1명에 동의하면 방장으로 지정한다. 동의하지 않아도 현재 회차는 예정대로 종료된다.
- 사람이 없거나 후보가 없으면 자동 승계하지 않는다. 계정 삭제를 양도 완료 전까지 막지 않는다.

### 13.3 취소·장애

- 시작 전 취소: 성적 없이 `cancelled`, 전원에게 통지.
- 시작 후: 방장 단독 취소·기간 변경 불가. 각자는 중도 종료 가능.
- 공통 장애: 서버 접수 증거가 있는 요청을 우선 복원한다. 접수 자체가 없는 운동을 추정하여 출석시키지 않는다.
- 판정 신뢰성을 보장할 수 없는 장애는 운영자가 영향 범위를 기록하고 회차를 `review_required` 또는 `voided`로 처리한다. 몰래 목표를 줄이거나 종료일을 연장하지 않는다.
- 보류가 24시간을 넘으면 운영 경고와 사용자 상태 안내를 갱신한다. 자동 작업은 무한 재시도하지 않으며 운영 검토 전까지 미달 확정을 강행하지 않는다.

### 13.4 읽기 갱신과 응답 없음

방 화면 진입·포그라운드 복귀·인증 완료·수동 새로고침 때 최신 상태를 조회한다. 열린 방 화면만 30초 간격으로 갱신하고 백그라운드에서는 중단한다. v1은 실시간 소켓 연결을 전제하지 않는다.

요청 시간 초과 시 마지막 갱신 시각과 “갱신하지 못했습니다”를 표시한다. 개시·동의·재촉·참여 요청은 응답이 없어도 즉시 새 요청 ID로 반복하지 않고 기존 요청의 처리 상태를 조회한다. 일반 API 12초·사진 업로드 45초라는 기존 클라이언트 제한과 맞춘다. 실패 작업은 최대 2회 재시도 후 로그·복구 대상으로 남긴다.

## 14. 화면과 동작

기존 하단 `오늘·운동·기록`은 유지하고 오늘 화면에 `내 챌린지` 진입점을 둔다. 초대 링크와 알림은 해당 방으로 직접 이동한다. 방 기능의 사용 비중이 확인되면 별도 하단 탭을 검토한다.

| 화면 | 주요 내용 | 주요 동작 |
| --- | --- | --- |
| 내 챌린지 | 참가 중·개시 대기·후속 제안·완료 방 | 방 만들기, 코드 입력 |
| 초대 웹페이지 | 방 안내·목표 초안·설치 버튼·코드 | 앱 열기, 코드 복사 |
| 대기실 | 참가 후보·정원·초대 상태·룰북 작성 상태 | 초대, 나가기 |
| 룰북 작성·열람 | 구조화된 규칙·버전·공개 범위 | 게시, 동의, 동의 철회 |
| 개시 확인 | 확정 명단·동의 상태·시작과 마감 | 개시 예약, 준비 부족 사유 확인 |
| 방 진행 | 내 진도·구간 일정·구성원 출석 | 인증, 개인별 근거, 재촉 |
| 참가자 상세 | 인정 날짜·종류·잠정 상태·공개된 운동 시간·상세 데이터 | 본인 공개 설정, 방장 재촉 |
| 운동 타이머 | 경과 시간·일시정지·동기화·측정 상태 | 시작, 일시정지, 재개, 종료, 보정 |
| 평가 근거 | 인정·불인정 내역·계산식·평가 버전 | 기술 오류 문의 |
| 결과 | 개인·방 최종 결과·구간별 근거 | 공유, 이어하기 |
| 다음 회차 | 복사된 룰북·참여 응답·새 명단 | 참여 동의, 거절 |
| 알림함 | 방장 재촉·개시·결과·후속 제안 | 해당 방 열기, 방해 금지 시간 설정 |

진행 화면 예시:

```text
퇴근 후 운동방 · 2회차
10/05~10/18 · 사진 필수 · 구간마다 3일

현재 1구간: 10/05~10/11
목표 충족 2명 / 참가자 5명 · 잠정
마지막 갱신 19:42

나       2/3일 · 1일 남음
참가자 A 3/3일 · 목표 충족
참가자 B 1/3일 · 진행 중
참가자 C 0/3일 · 오늘 휴식

[내 운동 인증]  [룰북 보기]
방장: [지금 재촉 가능한 참가자 확인]
```

퍼센트에는 항상 실제 횟수와 구간을 같이 표시한다. 색상만으로 상태를 구분하지 않고 텍스트를 병기한다. 운동 시간에는 타이머 기록·사용자 기록·미측정·확인 필요를 구분한다. `푸시 읽음`, `센서로 검증된 운동 시간`, `운동 수행 검증 완료`처럼 수집·검증하지 않은 정보는 표시하지 않는다.

| `notification_inbox` | 사용자에게 표시할 알림·생성 시각·본인 읽음 상태. 방장에게 읽음 공개 안 함 |

필수 제약:

- 회차별 사용자 1명, `(round_id, user_id, evaluation_date)` 유효 출석 최대 1개.
- 같은 제출 ID에 다른 내용이 들어오면 충돌 반환. 반복 전송으로 새 출석·새 알림을 만들지 않음.
- 방당 후속 초안·동의·예약 회차 최대 1개, 인정 기간 중첩 금지.
- 사용자별 예약·활성 회차 동시 참여 상한 3개. 같은 사용자 잠금으로 경합 처리.
- 개시·동의·명단 변경은 동일 회차 잠금 또는 버전 검증으로 직렬화.
- 완료 인증 이벤트와 원천 기록 변경은 한 트랜잭션에 저장. 원장 반영이 비동기라면 outbox와 멱등 소비자로 복구.
- 구간 마감 작업은 인증 수락과 동일한 잠금 경계를 사용. 마감 전에 수락된 진행 중 트랜잭션을 누락한 채 확정하지 않음.
- 최종 정산은 `source_watermark`까지 모든 인증 이벤트 반영을 확인한 뒤 확정. 로그만 남기고 누락 상태에서 확정 금지.
- 일일 알림 상한은 기기 단위가 아닌 사용자 단위로 잠금·계산. 발송 대기 건도 한도를 예약해 동시 요청 초과를 방지.
- 외부 발송 접수 여부가 불명확한 재시도는 이미 사용한 한도와 같은 이벤트를 유지한다. 전송 전 취소 건은 한도 예약을 해제할 수 있다.
- 초대 정원·조회 권한·동의 철회는 프런트엔드가 아니라 서버에서 강제.
- 사용자별 활성 타이머 최대 1개, `running` 타이머의 열린 구간 최대 1개. 종료된 구간끼리 중첩·음수 길이를 허용하지 않음.
- 타이머 명령은 `request_id`와 `revision`으로 중복·다중 기기 경합을 처리. 다른 계정의 타이머 접근 차단.
- 룰북 버전 저장·게시 사건·알림함·outbox 생성을 원자적으로 처리. 게시 재요청은 버전·알림을 중복 생성하지 않음.

## 17. 개발 순서와 MVP 완료 조건

### 단계 1: 약속 합의와 일정

방·회차·초대 코드·대기실·룰북 버전·참여 동의·개시 예약을 구현한다. 시간대·명단 경합·기간 중첩 검증을 먼저 완료한다. 코드 입력으로 전체 흐름을 검증한 뒤 HTTPS 초대장과 앱 링크를 연결한다.

### 단계 2: 인증과 평가

기존 개인 인증에 인증 이벤트·회차 원장 연결을 추가한다. 사진 보강·당일 휴식 복귀·운동 타이머·일시정지·오프라인 종료 복구·시간 공유·구간별 계산·정산·결과 스냅샷을 구현한다. 사용자 본인과 방장 데이터 조회 범위를 분리한다. 시간 측정이 출석 판정을 암묵적으로 바꾸지 않는지 검증한다.

### 단계 3: 이어하기와 운영

후속 회차 제안·재동의·방장 양도·중도 종료·기술 오류 처리·공개 동의 철회를 연결한다. 이전 회차 결과가 바뀌지 않는지 검증한다.

### 단계 4: 원격 알림

서버 알림함·기기 토큰·FCM/APNs·발송 작업자·한도·발송 전 재확인을 구현한다. 룰북 공식 게시 사건에 참가 후보 알림을 연결하고, 알림 클릭 후 세션 복원·최신 룰북 동의를 실기기에서 검증한다. 토큰 설정이 없는 상태에서는 UI에 원격 푸시가 가능한 것처럼 표시하지 않는다.

네 단계가 연결되면 이 문서의 주요 범위가 완성된다. 채팅, 공개 방 검색, 현금 내기, 임의 벌칙 집행, 운동량 순위, AI 사진 진위 판별, 자동 설치 후 링크 복원은 후속 범위다.

| 47 | 회차 정산 후 개인 시간 보정 | 확정 시간 스냅샷·출석 성패 불변, 공유 권한 철회는 즉시 반영 |
| 48 | 룰북 초안 저장·게시 실패 | 참가자에게 게시 알림 없음 |
| 49 | 룰북 공식 게시 성공·같은 요청 재전송 | 동일 버전·참가자당 알림 1건, 가입 전 사용자·방장 제외 |
| 50 | 참가자 앱이 종료된 상태에서 룰북 게시 | 원격 푸시 경로 검증, 로컬 알림만으로 가능하다고 판정하지 않음 |
| 51 | 푸시 권한 거부 상태에서 룰북 게시 | 알림함·다음 접속 배너에 표시, 게시와 참여 동의는 가능 |
| 52 | 새 룰북 게시 후 이전 알림 클릭 | 최신 룰북으로 이동, 이전 버전 동의 요청 거부 |
| 53 | 룰북 알림 대기 중 최신 버전 동의·탈퇴 | 불필요한 발송 취소, 게시 이력 유지 |
| 54 | 포그라운드에서 룰북 원격 알림 수신 | 앱 배너와 별도 로컬 OS 알림 중복 표시 없음 |

문서 작성 단계에서는 위 시나리오를 실행한 것이 아니다. 구현 완료 판정은 API·권한·시간 경계 검증 및 Android/iOS 실제 푸시 확인을 포함한다. 임시 테스트 파일은 프로젝트 지침에 따라 검증 후 삭제하고 결과 로그만 남긴다.

## 19. 운영 지표

- 초대 미리보기 → 대기실 가입 → 룰북 동의 → 개시 참가 전환.
- 방 개설부터 개시까지 걸린 시간, 미개시 원인(인원 부족·미동의·기한 경과).
- 첫 인증까지 걸린 시간, 구간별 목표 달성자 비율, 중도 종료 비율.
- 기존 참가자의 다음 회차 제안 수락률과 실제 재참여율.
- 재촉 요청 중 적격 비율, 한도 제외·수신 차단·발송 실패 비율.
- 재촉 후 24시간 내 인증은 관찰 지표로만 사용. 재촉 때문에 운동했다는 인과 효과로 해석하지 않음.
- 인증 반영 지연, 정산 보류, 결과 정정, 사진·상세 조회 권한 오류 건수.
- 타이머 시작→종료율, 종료 누락·오프라인 복구율, 출석일 중 시간 측정일 비율. 긴 운동 시간 자체를 성과로 해석하지 않음.
- 룰북 게시→동의 완료 시간, 게시 알림 접수·실패·최신 버전 대체 비율. 푸시 도착과 동의는 별도 사건으로 집계.

이 문서의 목표는 개설한 방 수를 늘리는 데서 끝나지 않는다. 합의한 규칙이 끝까지 유지되고, 각자의 실제 제출 기록에 따라 설명 가능한 결과가 나오며, 참가자가 다음 회차에 자발적으로 돌아오는지를 확인한다.

## 2026-10-08 확장: 종료 후 방장용 성장 리포트

이 절은 위 v1의 상세 기록·이전 기간 공유 범위를 요청된 성장 리포트에 한해 확장한다.
참가 동의 안내에 종료 후 방장이 인증 출석, 세트·중량·반복, 출발 기록을 직전 동일 길이 기간과
비교할 수 있음을 표시한다. 방장에게도 사진·개인 메모·체중·연락처·다른 방 정보는 공개하지 않는다.
전체 개인 리포트가 아니라 해당 두 기간의 성장 계산 근거만 제공한다.

`settling`과 `completed`의 방장 화면에 팀원별 리포트를 제공한다. 인증된 출석과 연결된 완료
운동의 종목별 세트, 반복, 운동량, 동일 조건 중량·반복 변화, 날짜별 수행 내역을 펼쳐 본다.
성장 점수는 중량·반복 30 + 세트 20 + 출석 20 + 시간 준수 20 + 추가 운동 10으로 계산한다.
총량·최대 중량은 별도로 표시하고, 동일 조건 및 운동일당 평균으로 성장 점수를 계산한다.
다른 팀원과의 중량 순위는 만들지 않는다.

이전·현재 각각 2일 이상의 종목 기록이 없거나 동일 중량/반복 조건이 맞지 않으면 비교 불가다.
비교 가능한 배점이 50점 미만이면 총점을 보류한다. 미비한 항목의 점수를 다른 항목에 재배분하지 않는다.
출석 완료만으로 시간 준수를 추정하지 않으며 미루기는 원래 약속 시각을 바꾸지 않는다.

시작 예약 때 저장한 개인 운동 요일을 두 기간에 동일 적용해 쉬는 요일 수행을 비교한다.
기존 회차의 과거 요일을 오늘 설정으로 추정하지 않으며 이 경우 주차별 목표 초과 출석을 사용한다.
결과 확정 때 성장 근거도 스냅샷으로 저장한다. 이미 확정된 예전 회차는 최초 조회 당시 남아 있는 기록으로
생성한 소급 리포트임을 표시한다. API 접근 권한·점수 상세 기준은 [서버 문서](../server/README.md)를 따른다.

## 2026-10-08 평가 기준 수정: growth_v2

이 절의 채점 기준이 앞선 growth_v1 설명을 대체한다.

- 출석 20점은 개인 주간 목표를 채우면 상한에 도달한다. 매 7일 구간에서 개인 목표를 초과한 출석은
  출석 배점에 더하지 않는다. 시작 예약 시 개인 요일 수를 사용하고, 해당 스냅샷이 없으면 시작 시점의
  개인 주간 목표 이력을 조회한다. 현재 설정이나 방 공통 목표로 과거 개인 목표를 추정하지 않는다.
- 중량·반복 30점과 세트 20점을 총중량 성장 50점으로 합친다. 총중량은 모든 세트의 중량 × 반복 합계다.
  직전 동일 길이 기간보다 10% 증가하면 25점, 20% 이상 증가하면 50점이다. 두 기간의 세트 기록이 각각
  2일 이상이고 이전 총중량이 양수여야 평가한다. 동일 종목·동일 반복 조건 비교는 참고 상세로 남긴다.
- 시간 준수 20점은 예정 시각부터 2시간 이내에 인증 완료한 날의 비율로 계산한다.
  예정 전 인증과 2시간 초과 인증은 제외하고 정확히 2시간은 포함한다. 출발 시각은 채점에 사용하지 않는다.
  미루기는 기준을 늦추지 않으며 챌린지에 인정된 인증 이벤트 시각을 사용한다.
- 추가 운동 성장 10점의 기준은 그대로 유지한다. 평가 불가 배점은 재분배하지 않으며 총점 보류 시에도
  산정 가능한 항목의 점수는 표시한다.

v1 확정 리포트는 비공개 이력에 보관하고 새 기준으로 한 번 재산정한다. 남아 있는 기록을 이용한
재산정임을 명시하며, 이후 v2 리포트는 고정된다. 기존 챌린지 출석 목표의 공식 달성 결과는 변경하지 않는다.
